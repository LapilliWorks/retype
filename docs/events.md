# Filesystem events

Generated by the probe, not written by hand:

```
cargo run -p retype-core --example probe_events
```

Each run creates a temporary directory, watches it, and replays a scenario suite. Scenarios are split into a setup and an action so the correlation starts from a primed state, the way it does in the daemon when a file has existed for a while. For each action it prints the raw events, then what the name-pair strategy concluded, then what the identity strategy concluded.

## 1. Linux (inotify, notify 8)

Measured 2026-10-29.

### 1.1 Raw events

An in-place rename produces three rename events, not one:

```
Modify(Name(From))   a.heic
Modify(Name(To))     a.jpg
Modify(Name(Both))   a.heic -> a.jpg
```

Alongside them, ordinary noise: `Create(File)`, `Access(Open(Any))`, `Modify(Data(Any))`, `Access(Close(Write))`. The dataless events matter only because they must be filtered: a rename followed by a write produces a second data event for the new name, and treating it as a trigger would convert twice.

### 1.2 Scenario results

| Scenario | Pair strategy | Identity strategy |
|---|---|---|
| Rename in place | `a.heic -> a.jpg`, intent `jpg` | Same |
| Rename case only | none | none |
| Rename stem and extension | none | none |
| Rename across directories | none | none |
| Two renames in one window | two facts: `e.heic -> e.jpg`, `e.jpg -> e.webp` | one fact: `e.heic -> e.webp`, intent `webp` |
| Rename over an existing file | `f.heic -> f.jpg` | Same |
| Twenty renames in one gesture | twenty facts | twenty facts |
| Rename then write | `h.heic -> h.jpg`, once | Same, once |
| Rename then delete | `i.heic -> i.jpg` | none |

### 1.3 What this establishes

- **Identity correlation and name pairing agree on the simple cases**, so the fallback is safe
- **They disagree on double renames, and identity is right.** The user's final intent was `webp`; the intermediate `jpg` never existed for long enough to convert, and converting it would produce a file the user did not ask for. Identity reports the net rename
- **Rename then delete yields nothing under identity**, which is correct and is worth relying on: the file is gone, so there is nothing to convert. The pair strategy would report a job for a path that no longer exists, and the dispatcher would have to fail it
- **The filters behave**: case-only, stem change and cross-directory produce no fact under either strategy, per
- **Batches are fine**: twenty renames in one gesture yield twenty facts, no loss, which the previous debouncer-based design could not promise
- **Data events must be filtered**: a write after a rename arrives as an ordinary modify, and it is not a second trigger

### 1.4 Feed order

Discovered by the probe, and the reason it is written down: the identity strategy silently produced nothing until the feed order was fixed.

Within one debounced batch, appearances must be observed **before** disappearances. A rename reports the old path as gone; feeding that first discards the identity mapping before the new path can claim it, and the rename is lost. The daemon obligation is:

1. Observe every path in the batch that exists now
2. Forget every path in the batch that no longer exists

Getting this backwards is invisible on Linux, because inotify also reports both names, and fatal on any platform that does not.

## 3. Windows (ReadDirectoryChangesW)

Not yet measured. Run the probe on Windows and replace this section. Two known gaps before that run:

- `std` does not expose a file id on Windows, so the probe reports identity as unavailable. Measurement needs the file id through `GetFileInformationByHandle`, which is experiment 4 on the plan's list
- The backend reports `From` then `To`, so the pair strategy is expected to work; the question is whether it ever reports more than one pending rename, which is where the debouncer used to lose pairs

## 4. BSD (kqueue)

Not yet measured, and not before the port. The backend reports a single-path `Any` event, which makes identity correlation load bearing, as on macOS.
